## 1. Jane Street — 抖动是被测量出来的，不是被声称的

**来源**：<https://www.janestreet.com/tech-talks/system-jitter-and-where-to-find-it/>
（Tudor Brindus 演讲，2026-07-27 访问）

**公开陈述（事实）**：该演讲用两个进程间的 ring-buffer 消息传递基准，在写入时取
T1、读取完成时取 T2，把**抖动定义为相对中位延迟的方差**，并逐项定位来源：

| 措施 | 公开给出的效果 |
| --- | --- |
| 去虚拟化，跑裸金属 | 637ns → 223ns |
| `isolcpus` 隔离网卡中断 | 再降 29ns |
| `nohz_full` 消除每秒约 1000 次时钟中断 | 消除 1 微秒处的显著抖动峰 |
| 关闭 turbo boost | 消除变频抖动（以吞吐换确定性） |
| 插入 x86 `pause` 提示 | bad speculation 由 8% 降至 1% |

最终：637ns 中位数 + 极大抖动 → 163ns + 极小方差。

**本报告的工程推论**：延迟工作的第一性动作是**建立可复现的测量装置**，而不是
优化代码。上表每一项都是"先测出分布，再定位来源，再验证改善"。

**对 QuantAgent 是否适用**：

- ✅ **适用**：延迟必须以分布（p50/p95/p99/p99.9/max）而非均值报告；丢事件数必须
  计数。本仓库的 `check_clock_drift` 已按此输出，快慢路径设计要求记录事件率、
  队列深度、丢弃计数。
- ❌ **不适用**：`isolcpus` / `nohz_full` / 关 turbo 这类内核调优，针对的是纳秒级
  做市场景。本仓库当前的数据源是**3 秒聚合**，纳秒级调优在这里没有任何意义——
  在 3 秒粒度上讨论 29ns 是荒谬的。**先解决数据粒度，再谈延迟。**

## 2. Two Sigma — 数据即代码

**来源**：<https://www.twosigma.com/articles/treating-data-as-code-at-two-sigma/>
（2026-07-27 访问）

**公开陈述（事实）**：将四条软件工程原则用于数据管理——版本化（数据集与处理设施
同时版本化以支持 replay）、测试（用 dbt 测 SQL，数据质量平台产出覆盖率指标）、
可复现性、血缘。原文强调：

> "understanding how data pipeline dependencies (DAGs) change over time and
> tracking data lineage has become foundational"

> 这一可见性 "is achieved by treating data as code and validating the process
> using software development practices like CI/CD."

**本报告的工程推论**：数据质量必须像代码一样有**自动化断言与覆盖率**，否则
"数据没问题"只是一句主观判断。

**对 QuantAgent 是否适用**：

- ✅ **高度适用，且已落地**：
  - 每个数据集带 `DataManifest`（provider、来源路径、行数、日期范围、schema 报告、
    PIT 违规、重复率、内容哈希）；
  - 本次新增的 `integrity.py` 输出 PASS/WARN/FAIL/**NOT_RUN** 四值判定，且
    `NOT_RUN` 不计为通过——这正是"覆盖率作为自然副产品"的直接体现：未评估的检查
    会拉低 `usable`；
  - Gold 构建记录 `adjustment_factor_version` 与 `content_hash`，可复现命令写入
    manifest。
- 📌 **差距**：本仓库尚无 CI 上的自动数据检查（当前靠人工触发脚本）。这是一条
  明确可执行的改进项。

## 3. Optiver — 影响半径与确定性仿真

**来源**：<https://www.optiver.com/what-we-do/technology/>（2026-07-27 访问）

**公开陈述（事实）**：官方技术页面公开强调低延迟系统、风险与交易系统的紧密集成，
以及对工程与研究协作的重视。

**本报告明确声明**：该页面属于**招聘与品牌性质**，不含可复核的架构细节。因此下面
是**推论而非事实**：

**工程推论**：把风险检查放在执行路径**内部**（而非事后对账）是可迁移的；把故障
影响限制在单一组件（blast radius）同样可迁移。

**对 QuantAgent 是否适用**：

- ✅ 已落地：`AShareMicrostructureSimulator` 在下单前调用 `rules.tradability()`，
  T+1、涨跌停、停牌在**成交模型内部**否决，而不是回测后再过滤；
- ✅ 已落地：行情读取（`xtdata_market_provider`）与执行（`qmt_gateway`）在导入图
  层面隔离，由 AST 测试强制——这是最小化影响半径的具体实现。

**公开陈述（事实）**：这些页面公开描述了研究、工程与交易的协作模式，以及对数据
管道、数据编目、访问控制、系统化研究平台的重视。

**本报告明确声明**：以上均为**职位与文化描述**，**不含**任何可复核的系统设计。
本报告**不**从中推断具体架构，只提取一条组织层面的原则：

**工程推论**：研究与生产使用**同一套数据与执行假设**，是避免"研究里赚钱、生产里
不赚钱"的结构性前提。

**对 QuantAgent 是否适用**：

- ✅ 已落地：唯一可信评测入口是 `scripts/baseline_protocol.py` variant C，且守卫
  fail-closed；任何数字引用须带 trust class。
- ✅ 本次强化：回测保真度由数据**推导**（`decide_fidelity`），策略作者无法自选，
  从机制上消除了"研究用乐观假设、生产用悲观假设"的缝隙。
