## 2. 诚实性审查 / Honesty audit（铁律：产物缺失即缺失）

**基础设施是好的**：`apps/quant-ui/src/utils/format.ts:1-47` 的 `formatPercent` /
`formatNumber` / `formatCompact` / `formatBytes` / `formatDate` 对
`null | undefined | NaN` **一律返回 `"暂无"`**，不返回 `0.00%`。

## 5. Bundle 体积前后对比 / Bundle size before & after

命令：`npm run build:vite`（vite 6.4.2）。

| chunk | 修改前 | 修改后 |
|---|---|---|
| `EChart` | **651.57 kB**（gzip 219.97）**⚠ 超 500 kB 警告** | 2.95 kB（gzip 1.25）—— 只剩组件本体 |
| `vendor-echarts` | — | **648.90 kB**（gzip 218.97）**⚠ 仍超警告** |
| `vendor-react` | —（混在 index 里） | 232.71 kB（gzip 74.30） |
| `vendor-query` | —（混在 index 里） | 38.65 kB（gzip 11.70） |
| `index`（应用代码，关键路径） | 492.08 kB（gzip 144.57） | **220.41 kB（gzip 58.56）** −55.2% |
| 构建耗时 | 5.40 s | 5.41 s |

**诚实结论：echarts 那一坨没有变小，因为它本来就那么大**（同一份代码换了个 chunk 名）。
真正的收益有两条，都可测量：

1. **关键路径的应用代码减半**（492 → 220 kB，gzip 144.57 → 58.56）。
2. **vendor chunk 文件名不再随应用改动变化** —— 改一行 UI 不再让浏览器重下 649 kB 的 echarts。

**为什么没把 echarts 拆到 500 kB 以下（实测两次都失败）**：

| 尝试 | 结果 |
|---|---|
| `zrender` 单独成 chunk | 得到 `vendor-echarts 474.56 kB` + `vendor-zrender 176.29 kB`，**500 kB 警告消失**，但 Rollup 报 **`Circular chunk: vendor-echarts -> vendor-zrender -> vendor-echarts`** |
| 按 `echarts/lib/chart/` vs core 拆 | `vendor-echarts-charts 94.46 kB` + `vendor-echarts-core 557.19 kB`，**仍然超警告，且仍然循环** |

echarts 的内部依赖是**真实循环**的。用一个**模块初始化顺序隐患**换掉一个**体积警告**
不是改进，因此最终保持单一 `vendor-echarts` chunk，**警告原样留着，也没有用
`chunkSizeWarningLimit` 把它调静音**。真正的下一步是砍掉未使用的图表类型
（`GraphChart` 只被 playbook 16 用、`RadarChart` 只被 `RiskRadar` 用），
那需要 `EChart.tsx` 支持按需注册，属于独立改动。
